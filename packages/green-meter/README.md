# @deepseek-ai/dsh-green-meter

Token-profile energy and carbon estimation for agentic sessions. The plugin
observes durable `assistant/message` events, converts each step's disjoint
token accounting (`inputTokens`, `cacheReadTokens`, `outputTokens`,
`reasoningTokens`) into joules and grams CO2e using calibrated coefficient
profiles, appends one row per accounted step to a JSONL ledger under the
Harness home, registers the human-facing `/green` slash command and the
model-facing `green_meter` tool, contributes the `greenMeter` session
projection that drives the Web composer-dock readout, and can enforce a
per-session energy budget.

This is the estimate-only path: it never touches hardware and works against
any API-backed provider. Calibration sources, in order of preference:

1. **H20 request-level fits (primary)** — non-negative least squares over
   5125 conservation-filtered requests from the frozen H20 experiment dataset
   (Qwen3.5-27B / Gemma-4-31B-it, DABStep/Terminal-Bench/SWE-bench-Pro agentic
   workloads). Median relative errors 1.2–2.8%, R² ≥ 0.998. Profiles:
   `qwen-h20-instant`, `qwen-h20-thinking`, `gemma-h20-instant`,
   `gemma-h20-thinking`, plus model-level means `qwen-h20` / `gemma-h20`.
2. **Legacy RTX 3090 fits** — the `handoff-e2-v1` Qwen3-4B coefficients
   (`qwen3-4b-instruct`, `qwen3-4b-thinking`), kept for the original
   experiments.
3. **Proxy** — the mean of the four H20 per-config fits (`h20-proxy-v1`,
   evaluated at R² 0.982 / median error 12.4% on all 5125 requests), used for
   any unknown model and as the default.

The H20 fits are regenerated by `scripts/fit-h20-requests.py` from the frozen
dataset and the per-request attribution records in the H20 experiment backup;
`src/h20-profiles.generated.ts` is its output.

## Estimation formula

```
E = a * uncached_input_tokens + (b + c * context_tokens_est / 32768) * (output_tokens + reasoning_tokens)
carbon_g = E / 3.6e6 * carbon_factor_kg_per_kwh * 1000
```

The per-request context estimate is the request's own prompt surface (uncached
input plus cached reads) plus half of its own output — the scheduler hook's
`context_len` semantics at request level. Cached reads never accumulate across
requests, and the context term is capped at 64K (the largest context observed
in the calibration experiments), so longer contexts keep the 64K rate instead
of extrapolating a linear rent term out of range.

## Configuration

| Key | Default | Meaning |
|---|---|---|
| `profile` | `proxy` | Calibration profile: `qwen3-4b-*`, `qwen-h20-*`, `gemma-h20-*`, or `proxy`. Unknown keys fall back to `proxy`. |
| `carbonFactorKgPerKwh` | `0.5777` | Grid carbon intensity; China 2024 national average. |
| `dir` | `<DSH_HOME>/green-meter` | Ledger directory; rows append to `ledger.jsonl` inside it. |
| `budgetJ` | `0` (off) | Session energy budget in joules; when exceeded, `agent/pre-step` rejects new steps and injects one warning message. |

Environment fallbacks: `DSH_GREEN_PROFILE`, `DSH_GREEN_CARBON_FACTOR`,
`DSH_GREEN_DIR`, `DSH_GREEN_BUDGET_J`. Mount the plugin with a profile row in
the profile's `cordis.patch.yml`:

```yaml
- insert:
    - id: green-meter
      name: '@deepseek-ai/dsh-green-meter'
      config:
        profile: proxy
        carbonFactorKgPerKwh: 0.5777
        budgetJ: 0
```

## Surfaces

- **`/green`** — human-facing report: requests, token totals (cached reads and
  reasoning split out), estimated energy (J/kWh), carbon (g CO2e), J per
  output token, per-turn breakdown, fit quality, budget status, and the
  method boundary.
- **`green_meter` tool** — the model can query its own session's cumulative
  estimate and budget state (Agents-for-Systems self-awareness).
- **`greenMeter` session projection + `dsh-client-ui-green-meter`** — the
  always-visible energy/carbon readout in the composer dock; updated by
  session/projection pushes, no polling.
- **Energy budget** — `budgetJ > 0` arms a `agent/pre-step` guard that rejects
  new steps once the session estimate exceeds the budget; one plugin-sourced
  warning is injected so the model sees why the turn closed.

## Ledger

One JSONL row per accounted step, schema `dsh-green-meter.step.v1`:

```json
{"schema_version":"dsh-green-meter.step.v1","ts_wall":"2026-08-13T12:00:00.000Z",
 "session_id":"session-…","turn":2,"step":1,"input_tokens":1200,
 "cached_read_tokens":9800,"output_tokens":800,"reasoning_tokens":200,
 "context_tokens_est":11200,"energy_j":3120.4,"carbon_g":0.5,
 "profile_id":"handoff-e2-proxy-v1","confidence":"proxy","method":"token-profile-estimate"}
```

The ledger is the authoritative aggregation source: `/green` re-reads the file
so a plugin reload (HMR) mid-session cannot lose or double-count history.
Malformed or foreign-schema lines are skipped at read time. The in-memory
tracker only carries the per-session context estimate, which resets on reload.

## Slash command

`/green` renders, for the receiving session: accounted requests, input/output
token totals (cached reads and reasoning split out), estimated energy (J/kWh),
estimated carbon (g CO2e), mean energy per output token, a per-turn energy
breakdown (last 10 turns), the ledger path, and the method-boundary note.

## Method boundaries

- **Scope:** modeled GPU operational energy, from token counts. No CPU/RAPL,
  no host DRAM, no cooling/PUE, no embodied or manufacturing carbon.
- **Carbon** is an engineering estimate: energy x a configurable grid factor;
  it is not a certified measurement.
- **Calibration** is fitted on RTX 3090 / BF16 / vLLM 0.9.2 / Qwen3-4B; any
  other model or hardware (including API-side inference on other provider
  hardware) is a proxy extrapolation, not a measurement. Measured attribution
  requires the vLLM green-meter plugin, whose ledger can be joined later via
  session-scoped task tags.
- **Context estimate** is a per-request approximation (prompt plus half the
  output) and is capped at the 64K calibration ceiling; sessions with larger
  contexts are billed at the 64K rate.

## Model Experience

None, as the plugin only observes `assistant/message` usage and renders
human-facing `/green` command output, appending no surface events and adding
no model-visible content.

#### KV Cache effect

Independent — the plugin neither reads nor mutates the request surface, so
prompt stability and provider-side cache reuse are unaffected.

## Known Limitations and Deferred Work

- **Estimate-only path** — no hardware measurement; a future provider could
  join the vLLM green-meter ledger on session ids for measured attribution.
- **Per-session scope** — subagent/fork lineage is not aggregated into a
  task-level total; each session's energy stays under its own id.
- **No UI widget yet** — the report lives in the `/green` command and the
  ledger file; a Web client plugin can project the ledger later.
- **Context drift** — compaction and plugin reloads reset or over-estimate the
  context-length input to the decode-cost term.
